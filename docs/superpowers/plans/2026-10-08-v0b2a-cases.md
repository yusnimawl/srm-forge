# v0b-2a: Cases and Analysis Plots Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** JMAG-style cases in the web tool — open a candidate, a reference design or a setup file as a case, edit its inputs with live validation and the motor diagram, Evaluate (always into a new case), EM-Validate, export/import, a cases table with overlays — plus the Performance, Map and Design-factors analysis tabs.

**Architecture:** `srmapp` gains case inputs, single-design evaluation (Auto/Fixed winding), EM validation of a case and map-derived design curves. `srmweb` gains a v2 store schema (cases, typed results, map times), `evaluate`/`validate` job kinds, case routes, setup files and typed response models so the generated TypeScript covers results. `web/` gains Cases and Case pages and shared analysis tabs.

**Tech Stack:** as v0b-1 (Python 3.12+, FastAPI, stdlib `sqlite3`, scipy for MAT; React 19, Vite, TypeScript, Tailwind v4, shadcn on Base UI, TanStack Query/Table, react-router 7, Plotly via `PlotlyPlot.tsx`, openapi-typescript, Vitest).

**Spec:** `docs/superpowers/specs/2026-10-08-v0b-web-design.md` — v0b-2a row of §2; §4.1 (case routes), §5, §6.2, §6.4, §6.5, §6.7 (`map_curves` only), §7.3 (Case, Cases), §7.4, §7.6, §7.10 (Performance without line current and power factor, Map, Design factors), §10, §11.

**Not in this plan:** drive waveforms, line current, power factor, the Waveforms and Field tabs, the quick lane (v0b-2b); sweep and design study (v0b-3).

## Global Constraints

- Package version stays `0.4.0`; `srmcore` is not modified. `srmweb.__version__` and `web/package.json` go to `"0.2.0"`.
- Layering: `srmweb` may import `srmapp` and `srmcore` public modules; `srmapp`/`srmcore` never import `srmweb`; `srmweb` never imports `gmsh`, `ngsolve`, `netgen`, `skfem` directly. `srmapp`/`srmcore` import without the `web` extra.
- SI inside Python and the API; the UI converts only through `web/src/lib/units.ts` (`fromSI`/`toSI`/`fmtSI`).
- Every result view shows **"Unvalidated, peak-only"** unless the case carries the EM-validated label, then **"EM-validated"** with the engine version.
- Request models `extra="forbid"`, bounded fields; 422 with field paths for invalid input.
- Any task that changes a route or a schema regenerates `web/openapi.json` (`python -m srmweb.openapi web/openapi.json`) and `web/src/api/schema.ts` (`cd web && npm run gen:api`) in the same commit.
- Python test files in `tests/web/` (`test_web_*.py`) and `tests/app/` (`test_app_*.py`); basenames unique. Comments describe the code as it is.
- Case overlays: at most 6 cases, colour **and** line style (solid, dashed, dotted).
- Map-time fallback when no history exists: `screening` 228 s, `full` 1560 s (M5e2 figures, 8/6 at 8 workers).

## Review Focus

1. Editing an evaluated case must never change it: the first edit creates a draft child case (`origin "edit"`, `parent_case_id` set) → tests in Task 6 (`test_patch_inputs_of_evaluated_case_409`) and Task 12 (draft created on first edit).
2. EM Validate on a draft or a `screening` case must refuse with a clear message, not start a one-hour job that fails → test in Task 7 (`test_validate_refuses_stale_or_screening`).
3. A setup file with an unknown key, the wrong `schema`, or a winding whose wire index is outside the requirements' wire list must come back as field errors, never a crash → tests in Task 8.
4. Deleting a search run must keep the cases opened from it; deleting a case while its job runs must be refused → tests in Task 4 and Task 6.
5. Opening the tool on a v0b-1 database must keep every past run → test in Task 4 (`test_v1_database_migrates_and_keeps_runs`).

### Task 7: Live validation, Evaluate, EM Validate, map estimate, MAT export

**Files:**
- Modify: `src/srmweb/api.py`, `src/srmweb/schemas.py`
- Test: `tests/web/test_web_case_actions.py`

**Interfaces:**
- Consumes: Tasks 2, 4, 5, 6.
- Routes:
  - `POST /api/validate` body `{"inputs": <any JSON>}` → 200 `{"errors": [{"loc": [...], "msg": str}], "warnings": [{"loc", "msg"}]}`, never 422: Pydantic errors of `CaseInputs` (loc relative to `inputs`), then `validate_params` issues (loc `["design", "machine", <parameter>]`, msg `"[<rule>] <message>"`), then `map_request` failures (fixed winding `ValueError` → loc `["winding", <field>]`), then the stage-1 reason as a warning (loc `[]`).
  - `POST /api/cases/{id}/evaluate` (optional body `{"grid": [angles, currents]}`, same bounds as `SearchRequest.grid`, test-only) → 201 `{"job_id"}`; 409 when the case is not stale; 422 with the `/validate` errors when it has any; 429 on a full queue.
  - `POST /api/cases/{id}/validate` → 201 `{"job_id"}`; 409 `"evaluate this case first"` when stale or without an evaluation; 409 `"EM validation needs a full map"` when the preset is `screening`.
  - `GET /api/cases/{id}/estimate` → `{"new_map": bool, "seconds": float | None, "basis": "history" | "budget" | null}` — `map_cache_hit`; seconds = mean of `recent_map_times(preset)` or the Global-Constraints fallback.
