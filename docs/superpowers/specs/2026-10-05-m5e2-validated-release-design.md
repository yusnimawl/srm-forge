# M5e2: library adds, map identity, speed budgets, validation report, CI slow suite, validated release

Date: 2026-10-05. Closes M5 (core spec §2.3, §5.3, §7.2, §8.4–8.6, §9). Builds on M5e1 (`docs/superpowers/specs/2026-10-05-m5e1-label-budget-design.md`).

## Goal

srmcore **0.4.0** is the first version in `VALIDATED_VERSIONS`, so `em_validate` can award "EM-validated". Before that, a generated validation report must pass, and the fast and slow suites must be green on Windows and Linux.

## Owner decisions (2026-10-05)

1. **Library data:** downloaded public datasheets, curves traced or read in this repo, grade B or C as below. Source PDFs are committed.
2. **Speed budgets:** re-baselined to measured times. The budget is the measured worst case × 1.25, rounded up. "Met" means the benchmark is under budget. No accuracy is traded for speed.
3. **CI:** the repo stays private (no paid minutes). The slow suite runs on `v*` tags and manual dispatch only. On push, the fast suite runs Linux 3.12 and Windows 3.12; PRs and tags run the full 2 × 2 matrix.
4. **Report:** generated by `tools/validation_report.py` from committed result JSONs, and regenerated on every version bump before tagging.
5. **Map identity:** `MapResult` carries `design_hash` and `preset`; `em_validate` checks the hash.
6. **Hiperco 50HS:** three anneal variants, grade C. No unannealed variant, because Carpenter publishes no B-H for the as-rolled state. The owner plans wire-EDM laminations (anneal the sheet, then EDM).
7. **Adaptive `reference` preset:** not built. The 8/6 passes the uniform `reference` point check (M5e1).

Notes:
- **10JNEX900 `digitisation_error`:** the traced DC curve is 2 % below JFE's catalogue table (B8 1.261 vs 1.29 T, B25 1.375 vs 1.40 T). The budget carries 0.025 as the combined tracing and source spread. The traced curve is used as is, never scaled to the table. Points above 20 kA/m are dropped: the traced curve there is flatter than μ0 and fails the polarisation check, and the tail to Js takes over. The 50 Hz catalogue curve (f2e-001 p. 9, 0.5–1.4 T) agrees with the DC curve to 0.0007 T on average, and is noted as a cross-check.
- **Hiperco 50A:** the chart nodes and the table agree within 1.5 %, which sets `digitisation_error`. μr at the 51.9 A/m node (≈ 21700) matches the datasheet μmax of 22000.
- **Hiperco 50HS:** below 800 A/m the curve is the B-H pipeline's interpolation from the origin, not data, which is why it is grade C. The provenance note says "no data below 800 A/m; no unannealed state". Cold-rolled 50HS must be annealed (Carpenter: 704–760 °C) before it is magnetically usable.
- **Stacking 0.95 (Hiperco):** neither Carpenter sheet gives a stacking factor. 0.95 is flagged provisional, to be replaced with the supplier's value.
- Source PDFs are committed in `docs/sources/materials/` (private repo). `tools/digitise_bh.py` reproduces the 10JNEX900 trace (and the Hiperco 50A vector-node read) from those PDFs and prints the points. It needs PyMuPDF, a dev-only tool dependency added to the `[dev]` extra.
- Tests: the existing material tests are parametrized over `available_materials()`. They check that each record loads, that `process_bh` succeeds, that the knot error is below 1e-9, and that every table point is reproduced by `h_of_b`. Plus one test that grade-B records set `digitisation_error`. All of these run in milliseconds and stay in the fast suite.

## 2. Map identity

- `maps/run.py` `MapResult` gets two fields: `design_hash: str` and `preset: str`. `design_hash` = `maps.dataset.design_hash(design)`, a new function hashing the canonical design JSON, the resolved mesh settings and the stator and rotor material JSON bytes. These are the same ingredients `provenance` uses, minus the grids, the solver and the version. `run_map` takes the design and sets both fields. `build_map` passes them through, and so do `apply_failure_policy` and cancellation.
- `maps/dataset.py`: `write_map`/`read_map` store and read both fields. The schema version is bumped, so older cache files become misses (the existing foreign-schema rule).
- `maps/validation.py`:
  - New check `map_identity`: pass iff `result.design_hash == design_hash(design)`. It is part of the label, and the note names both hashes on a mismatch.
  - The `preset` check reads `result.preset` and requires it to equal the design's preset and to be `full` or `reference`.
  - `map_matches_design` stays as a second line. When the map's peak |torque| is 0, it fails with the note "map has zero peak torque" instead of dividing by zero.
- The overlap map (`OverlapResult`) is not used by `em_validate` and gets no new fields.
- Tests (fast): identity pass, identity mismatch (a design differing in one field), the zero-torque case, and an HDF5 round-trip of both fields. They use the existing tiny fixtures and monkeypatched solves.

## 3. Speed budgets

- `examples/speed_budget.py [--json out]`: on an idle machine with 8 workers and a cold cache, it times, for the 8/6 and the 12/8:
  - `screening`: `build_map` (40 × 8) plus `analyse_map`
  - `full`: `build_map` (48 × 20) plus `analyse_map`
  - `full` extras: `build_overlap_map` plus the held-out and band-radius checks (`fem_checks`, 64 held-out samples)

  It writes `docs/validation/speed.json` (machine, CPU, worker count, srmcore version, seconds per item).
- Budget per row = max over the two designs × 1.25, rounded up to the next minute (the next 10 s for `screening`). It goes into spec §7.2's table, and the old numbers move to §11 with the date.
- The report compares the measured times with the budgets. The benchmark is re-run for each release, on the owner's laptop.

## 4. Validation report

`tools/validation_report.py` (no FEM, seconds) reads committed JSON and writes `docs/validation-report.md` and PNGs in `docs/validation/`.

Inputs (each produced by an existing example script with a new `--json PATH` option, where it lacks one):

| Section | Source | Verdict |
|---|---|---|
| Engine | `importlib.metadata`: srmcore version, Python, the pinned versions and licences of numpy, scipy, gmsh, scikit-fem, ngsolve, netgen, h5py, pydantic | — |
| Material library | `available_materials()` records: grade, source, Js, stacking, digitisation, provisional fields | — |
| M5a mesh convergence | `docs/m5a-data/*.jsonl` (existing) | pass/fail against the 1.7 % held-out limit and the preset tolerances |
| M5b TEAM 24 | `examples/team24_check.py --json` | error ± uncertainty (reported, no gate) |
| M5c FEMM | `examples/femm_check.py --json` | pass/fail against §8.3 (ψ ±2 %, mid torque ±3 %, saturated torque ±5 %) |
| M5d Krishnan 6/4 | `examples/krishnan_6_4_check.py --json` | error ± uncertainty before and after the end-winding correction (reported, no gate) |
| 8/6 EM validation | `examples/em_validate_8_6.py --json` | every check's status and the budget table |
| Speed | `docs/validation/speed.json` and the §7.2 budgets | pass/fail |
| CI | the release tag's `slow.yml` run URL and result, entered by hand into `docs/validation/ci.json` | pass/fail |

Plots: the M5a convergence curves (copied or regenerated from the jsonl), the FEMM ψ and torque comparison, the Krishnan measured-vs-model bars, and a budget bar chart. They use matplotlib (dev extra).

**The report passes** when every gated row passes: M5a, M5c, speed, CI, and every `em_validate` check except `engine_version`. The report prints a top-line verdict (`PASS`/`FAIL` and the failing rows). Rows that are reported only (M5b, M5d) never fail it, but they print their residuals.

Test (fast): run the generator on a small synthetic input set in `tmp_path`, assert the verdict logic (one failing gated row → FAIL, a failing report-only row → still PASS) and that every section heading is present.

## 5. CI

- `.github/workflows/ci.yml`: the `fast` job matrix is the full 2 × 2 on `pull_request` and on `v*` tags. On `push` to branches it is Linux 3.12 and Windows 3.12, implemented with a matrix `include` chosen by `github.event_name` / `github.ref`.
- New `.github/workflows/slow.yml`: `on: push: tags: ['v*']` and `workflow_dispatch`. Matrix Windows and Linux, Python 3.12, `timeout-minutes: 360`. It installs the same packages as `fast` and runs `python -m pytest -m slow --durations=25`. FEMM is not installed, so the FEMM comparisons run from the committed fixtures, as today.
- Before the first tag: run `python -m pytest -m slow` locally on an idle machine, and record the wall time and peak memory in the handoff. The `em_validate` end-to-end test builds a `reference` mesh (about 612 k nodes, ~4 GB). GitHub's private Linux and Windows runners have 7 GB. If a CI job runs out of memory, the fix is decided then (owner decision); tests are not silently skipped.

## 6. Version and release order

1. Implement sections 1–5 on branch `m5e2-validated-release`. Bump `pyproject.toml` to 0.4.0 and reinstall (`pip install -e`), so `importlib.metadata` reports 0.4.0.
2. Run on the laptop (detached, per the process notes): `em_validate_8_6.py --json` (`full`, about 1 h), `speed_budget.py --json`, `femm_check.py --json`, `team24_check.py --json`, `krishnan_6_4_check.py --json`, then the slow suite locally.
3. Generate the report. It must print PASS except for `engine_version` and CI (CI is pending until the tag).
4. Add `"0.4.0"` to `VALIDATED_VERSIONS`. Re-run `em_validate_8_6.py --json`, which now awards the label, and regenerate the report.
5. Whole-branch review, local merge to `main` on the owner's yes, push.
6. Tag `v0.4.0` and push the tag. `slow.yml` runs on both OSes. Record the run in `docs/validation/ci.json` and regenerate the report (a docs-only commit). If the slow run fails, `"0.4.0"` is removed from `VALIDATED_VERSIONS` in a follow-up release, and the failure is recorded.
7. Spec §9: M5 row marked complete. §11: the M5e2 decisions. CLAUDE.md "Current state" updated. Living project doc updated.

## Risks

- The fast suite has about 10 s headroom under 10 min. New fast tests must be small. If the suite goes over 10 min, the owner decides (split it, raise the limit, or move tests to slow).
- CI slow-suite memory on 7 GB runners (section 5).
- Datasheet values are typical, not guaranteed. The grades and the budget carry this; grade A needs measured lot data.
